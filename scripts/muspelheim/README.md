# Стенд показа на MUSPELHEIM

Канон настройки площадки показа. Файлы здесь — источник правды: на самой
площадке лежат их копии в `C:\projects\meridius-watchdog\`, и правка делается
здесь, а потом раскладывается скриптом, а не наоборот.

## Как устроена цепочка

```
Tailscale Funnel :10000/qr  ──►  звено-прокси :3099  ──►  продукт :3100
```

Funnel при `--set-path=/qr` префикс **срезает**, поэтому между ним и продуктом
стоит звено, которое префикс возвращает (`C:\projects\meridius-qr-proxy\proxy.mjs`).
Продукт собран с `BASE_PATH=/qr` и на своём корне отдаёт 404 — это не поломка.

Отсюда адреса проверки живости, и менять их наугад нельзя:

| Звено   | Проверять           | Исправный ответ |
| ------- | ------------------- | --------------- |
| Продукт | `127.0.0.1:3100/qr` | 200             |
| Прокси  | `127.0.0.1:3099/`   | 200             |

## Задачи планировщика

| Задача              | Что делает                  | Когда стартует                      |
| ------------------- | --------------------------- | ----------------------------------- |
| `meridius-start`    | Продукт (`npm run start`)   | При загрузке, с задержкой 2 минуты  |
| `meridius-qr-proxy` | Звено, возвращающее префикс | При загрузке                        |
| `meridius-watchdog` | Сторож живости              | При загрузке и далее каждые 5 минут |

## Файлы

Лимит времени у задач продукта и звена — **снят** (`ExecutionTimeLimit = 0`), и
это не мелочь настройки: общий лимит в 10 минут убивал стенд каждые 10 минут,
а сторож поднимал его каждые 15 и писал в журнал «поднят, отвечает 200» —
снаружи это выглядело случайным 502 (issue #140). Лимит остаётся только у
сторожа, которому он служит предохранителем от зависшего прогона.

| Файл                | Назначение                                                    |
| ------------------- | ------------------------------------------------------------- |
| `install-tasks.ps1` | Приводит все три задачи в нужное состояние. Идемпотентен      |
| `watchdog.ps1`      | Проверяет оба звена и поднимает упавшее, пишет `watchdog.log` |

Разложить на площадке:

```bash
scp scripts/muspelheim/*.ps1 muspelheim:'C:/projects/meridius-watchdog/'
ssh muspelheim 'powershell -NoProfile -ExecutionPolicy Bypass -File C:\projects\meridius-watchdog\install-tasks.ps1'
```

Копировать нужно **с BOM**: PowerShell 5.1 читает `.ps1` без BOM как ANSI и
портит русские строки.

## Почему это появилось (issue #92)

15.09.2026 оба процесса стенда умерли с `ERROR_PROCESS_ABORTED`, планировщик
оставил задачи в `Ready` и не поднял их. Стенд простоял мёртвым двое суток, и
единственным сигналом оказался владелец, которому понадобилась ссылка.

Разбор показал три отдельных дефекта, и каждый чинится отдельно:

1. **У продукта не было триггера на загрузку** — стоял одноразовый `TimeTrigger`
   от 09.09.2026. После любого ребута стенд не поднимался вообще.
2. **Обеим задачам была запрещена работа от батареи** (`DisallowStartIfOnBatteries`
   плюс `StopIfGoingOnBatteries`), а площадка — ноутбук. Моргание питания гасило
   стенд молча.
3. **Не было проверки живости.** Её роль и выполняет сторож.

Проверено фактом 17.09.2026: задача продукта погашена намеренно, сторож заметил
это и вернул продукт за 43 секунды, снаружи `/qr` и `/qr/admin/login` — 200.

## Чего сторож не делает

Он **не сообщает владельцу**: чинит молча и пишет в лог. Если стенд начнёт падать
регулярно, это будет видно только в `watchdog.log` и по времени в `last-ok.txt`.
Сигнал в канал уведомлений — отдельная работа.

Он также **не следит за базой**: продукт без неё поднимется и будет отдавать 200
на части экранов. Проверка базы — тоже отдельная работа.
