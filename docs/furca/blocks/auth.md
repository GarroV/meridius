# Block: auth

## Назначение

Минимальный вход в админку: один аккаунт, пароль, сессия. Ровно столько, чтобы конструктор чек-листов не был открыт интернету — ролей и пользователей в MVP нет.

## API-контракт

```ts
requireAdmin(): Promise<void>            // бросает redirect на /admin/login, если сессии нет
signIn(password: string): Promise<SignInResult>
signOut(): Promise<void>

type SignInResult =
  | { status: "ok" }                                   // пароль верен, кука поставлена
  | { status: "rejected" }                             // пароль неверен, без подробностей
  | { status: "throttled"; retryAfterSeconds: number } // слишком много попыток подряд
```

Пароль хранится хэшем в `ADMIN_PASSWORD_HASH`, сессия — подписанная httpOnly-cookie на `SESSION_SECRET`, срок 30 дней. Маршрут `/s/*` этот блок не импортирует.

Где что лежит:

| Что | Файл |
|---|---|
| `requireAdmin()`, `hasAdminSession()` | `src/blocks/auth/guard.ts` |
| `signIn()`, `signOut()` (серверные действия) | `src/blocks/auth/actions.ts` |
| Хэш и проверка пароля | `src/blocks/auth/password.ts` |
| Подпись и разбор сессионной куки | `src/blocks/auth/session.ts` |
| Чтение переменных окружения | `src/blocks/auth/config.ts` |
| Счёт попыток входа: пределы, приговор, корзина клиента | `src/blocks/auth/rate-limit.ts` |
| Хранилище счёта: занятие места, снятие, уборка | `src/blocks/auth/attempt-store.ts` |
| Адреса `/admin/login` и `/admin` | `src/blocks/auth/routes.ts` |
| Экран входа | `src/blocks/auth/ui/` |

**Как этим пользуются другие блоки.** Экраны админки ничего не делают: они лежат в `src/app/admin/**` и закрыты сами. Серверные действия и обработчики `route.ts` зовут `requireAdmin()` первой строкой — разметка их не закрывает (см. ниже).

## Как устроена охрана

Два независимых рубежа. Первый отказывает до рендера, второй — на уровне данных; второй продолжает работать, даже если первый когда-нибудь потеряют.

- **Перед рендером.** `src/proxy.ts` (в Next 16 так называется бывший middleware) сторожит `/admin/:path*` и отдаёт переход на форму входа раньше, чем что-либо отрендерится. Без него запрос клиентской навигации (заголовок `RSC`) увозил разметку админки: разметка и страница рендерятся параллельно, поэтому `redirect()` из разметки страницу не отменяет — её содержимое уезжало в теле ответа вместе с редиректом. Найдено ревью безопасности, проверяется отдельными сценариями.
- **Экраны.** `src/app/admin/layout.tsx` зовёт `requireAdmin()`. Любой новый экран в `src/app/admin/**` попадает под охрану сам, правок здесь не требует.
- **Форма входа** живёт вне этого каталога — `src/app/(public)/admin/login/page.tsx`, адрес тот же `/admin/login`. Иначе охрана заворачивала бы форму входа на саму себя.
- **Неизвестные адреса** ловит `src/app/admin/[...unknown]/page.tsx`. Без него Next отвечает 404 раньше охраны, и перебор адресов показывает гостю, какие разделы в админке есть, а каких нет.
- **Чего разметка не закрывает:** серверные действия и обработчики `route.ts` выполняются мимо дерева разметки. Каждое такое место зовёт `requireAdmin()` само; что ни одно не забыто, проверяет `e2e/admin-guard.spec.ts` — он перебирает файлы маршрутов, а не записанный однажды список, и на незащищённом обработчике падает с именем файла.
- **Смена `SESSION_SECRET` разлогинивает всех.** Это единственный способ отозвать выданные сессии: хранилища сессий в MVP нет.

## Переменные окружения

Имена, назначение и безопасные значения для локальной разработки — в `.env.example`; рабочие значения только в `.env` (в `.gitignore`).

**Знак `$` в значениях переменных запрещён.** Окружение приложения собирает загрузчик `.env` самого Next (`@next/env`), а он прогоняет значения через подстановку `$переменная` — и те, что записаны в файле, и те, что уже стоят в окружении процесса, если файл упоминает то же имя. Делает это молча. Значение со знаком `$` доезжает до кода обрезанным; экранировать его можно как `\$`. Отсюда точка вместо `$` в формате хэша. Проверка на это — `src/blocks/auth/env-file.test.ts`, она гоняет настоящий загрузчик Next.

- `ADMIN_PASSWORD_HASH` — хэш пароля в формате `scrypt.N.r.p.соль.ключ`. Считается командой:

  ```bash
  node scripts/hash-admin-password.mjs        # ввести пароль, затем Ctrl-D
  printf '%s' 'пароль' | node scripts/hash-admin-password.mjs
  ```

  Пароль читается со стандартного ввода, а не из аргумента команды: аргумент виден и в истории оболочки, и в списке процессов.

  Пароль короче 12 знаков скрипт по умолчанию считать отказывается: вход в кабинет единственный,
  и подбор упирается только в длину. Отступление возможно, но осознанное — флагом `--allow-short`,
  и тогда скрипт печатает предупреждение. Молчаливого пути к короткому паролю нет: без флага — отказ,
  с флагом — предупреждение (D047: короткая учётка на время показа, значение — только в `.env` площадки).

- `SESSION_SECRET` — секрет подписи куки, не короче 32 знаков, свой на каждой площадке: `openssl rand -base64 48`.

Без любой из двух переменных вход падает с внятной ошибкой и **никого не пускает**; значения в текст ошибки не попадают.

В `.env.example` обе переменные заполнены значениями для локальной разработки (пароль `dodo-local-dev`). Секретом они не являются — файл лежит в git, — поэтому на `NODE_ENV=production` вход именно с этими значениями отказывает отдельной ошибкой: забытый на площадке пример иначе открыл бы админку любому читателю репозитория. Что константы в `config.ts` всё ещё совпадают с самим файлом, проверяет `config.test.ts`.

## Definition of Done блока

1. Любой маршрут `/admin/*` без сессии отдаёт форму входа, а не данные — проверено сквозным сценарием на каждом экране админки. **Закрыто:** `e2e/admin-guard.spec.ts` перебирает маршруты по файлам; сейчас это `/admin`, ловушка неизвестных адресов и отдельно проверенный несуществующий адрес. Каждый экран проверяется дважды — обычным запросом и запросом клиентской навигации, где смотрят не код ответа, а тело; отдельно проверены `HEAD` и предзагрузка ссылки роутером.
2. Неверный пароль не отличим по времени ответа от верного (сравнение постоянного времени). **Закрыто:** scrypt считается целиком всегда, ключи сравниваются `timingSafeEqual`; проверяется в `password.test.ts` сверкой самой работы, а не замером времени — см. T104.
3. Пароль и секрет не попадают в разметку, логи и сообщения об ошибках. **Закрыто:** тесты в `password.test.ts`, `actions.test.ts` и сквозной сценарий на разметку.
4. Публичный маршрут `/s/<код>` работает без сессии. **Закрыто наполовину:** проверено, что `/s/*` не заворачивается на вход (404 без редиректа) и не импортирует блок; сам маршрут появится с блоком `fill`.
5. `.env.example` содержит имена переменных. **Закрыто иначе, чем написано в контракте:** значения не пустые, а заполненные и безопасные — так требует конституция проекта («`.env.example` с именами и безопасными значениями обязателен: без него проект не поднять ни в другой сессии, ни другим человеком»). Пустые значения этому требованию не отвечали: скопировав пример, поднять проект было нельзя. Риск публичного пароля закрыт отказом на `NODE_ENV=production`.
6. Перебор пароля ограничен (T066). **Закрыто:** пять попыток с клиента за 15 минут и общий потолок в 50; человеку называется срок, когда можно повторить. Считаются попытки, а не промахи: место в счёте занимается до проверки пароля, иначе пришедшие разом запросы обходят предел все разом (T217).

Решения не принимались, расхождения вынесены наверх:

## Журнал работы

Исполнителей (`forge-executor`) не запускал ни разу: вся работа блока — аутентификация, а это прямое исключение из условия делегирования.

**T013 — вход в админку. Делал сам:** пароль, сравнение постоянного времени и подпись сессии — сердцевина безопасности блока, делить её на механические куски нечего.

- Пароль: scrypt из `node:crypto` (без новых зависимостей, карантин `.npmrc` не задет). Параметры `N=2^15, r=8, p=1` (OWASP) лежат внутри строки хэша, поэтому их можно сменить, не ломая старые значения; тесты считают на дешёвых параметрах.
- Постоянное время: scrypt считается всегда целиком, ключи сравниваются `timingSafeEqual`, длины совпадают по построению — раннего выхода нет ни по длине, ни по первому отличию.
- Сессия: `base64url(содержимое).HMAC-SHA256`, срок 30 дней, внутри только `iat`/`exp`. Подпись проверяется до разбора содержимого, разбор не верит подписи (тесты подписывают мусор своим же секретом).
- Кука: `httpOnly`, `sameSite=lax`, `path=/`, `maxAge` 30 дней, `secure` на площадке.
- **Проверено запуском:** 35 модульных тестов (пароль 12, сессия 13, действия входа 10); отдельно — прогон на заведомо сломанном коде: ранний выход по длине пароля валит замер времени (0,0008 мс против 13,1 мс), «испорченный хэш молча пускает» валит два теста, кука без `httpOnly` и пропущенная проверка пароля — ещё два.

**T014 — `requireAdmin()` и охрана `/admin/*`. Делал сам:** та же причина; кроме того, разбирался, почему Next отвечает 404 раньше охраны, — расследование, а не механическая работа.

- Охрана в разметке `src/app/admin/layout.tsx`, форма входа вынесена в группу `(public)`, неизвестные адреса ловит `[...unknown]`.
- Найдено по ходу: несуществующий адрес под `/admin` отвечал 404 **до** охраны, то есть перебор адресов отличал существующий раздел от несуществующего. Закрыто ловушкой; проверка на это осталась в наборе.
- Экран входа собран по эталону, оба языка, форма работает без JavaScript (действие серверное). Поле проверяется на границе: не строка, пусто или длиннее 512 знаков — тот же отказ без подробностей.
- **Проверено запуском:** 14 модульных (охрана 7, действие формы 7) и 20 сквозных сценариев; живой браузер — снимок экрана рядом с эталоном; прогон на поломке: снятая охрана валит четыре сквозных сценария, незащищённый `route.ts` под `/admin` валит свой и называет файл.
- Отдельно подтверждено, что вход работает с выключенным в браузере JavaScript: форма держится на серверном действии, а не на скриптах.
- **Полный прогон `./scripts/check`:** все семь проверок зелёные. Покрытие выросло относительно приёмки `core`: строки 78,26 % → 86,61 %, ветки 81,25 % → 83,52 %, инструкции 81,48 % → 87,09 %.

**Ревью безопасности (агент `security-reviewer`, только чтение).** Критических и высоких находок нет. По итогам сделано в блоке:

- Найдена и закрыта настоящая утечка: запрос клиентской навигации (`RSC`) к `/admin` без сессии возвращал в теле отрендеренную страницу админки вместе с редиректом. Сначала написан падающий сценарий, потом `src/proxy.ts`; после правки в теле того же запроса приходит экран входа. Проверка на это осталась в наборе для каждого маршрута админки.
- Параметры scrypt приведены к строке таблицы OWASP: `p` с 1 до 3 (37 мс → 113 мс на проверку). Прежний комментарий ссылался на OWASP, но пары `N=2^15` с `p=1` в той таблице нет.
- В `session.ts` записано, что отозвать выданную сессию можно только сменой `SESSION_SECRET`: подпись не зависит от пароля, и смена одного лишь пароля украденную куку не обесценивает.
- Добавлены сценарии на `HEAD` и предзагрузку ссылки роутером — ревью отметило, что эти пути не проверялись.
- Две находки вынесены наверх (заголовки CSP/X-Frame-Options и ограничение частоты попыток) — см. раздел выше.

**Что осталось за границей блока и не делалось:** ролей, областей видимости, восстановления пароля, второго фактора и таблиц пользователей нет (D014); ограничения частоты попыток входа контракт не требует — вынесено в отчёт диспетчеру, а не сделано молча.

### Волна исправлений: T063 и T066

**T063 — прогон не проходил ни в одном состоянии. Делал сам:** это расследование чужого молчаливого поведения, а не механическая работа с готовым контрактом.

*Что происходило.* Загрузчик `.env` самого Next (`@next/env`) прогоняет значения через подстановку `$переменная` из `dotenv-expand`. Причём не только строки из файла: если файл упоминает имя, которое уже стоит в окружении процесса, через подстановку прогоняется и значение из окружения. Всё, что похоже на `$имя`, заменяется пустотой — молча, без строки в логе. Замерено на настоящем загрузчике до правки:

```
было : scrypt$32768$8$1$VEBPqyZizNCu1bBmEgQQoQ$ew-dS1kNOX5bnC4kEI-p5xLrSb_misQXVp5VTUB_V1o
стало: scrypt-dS1kNOX5bnC4kEI-p5xLrSb_misQXVp5VTUB_V1o
```

Отсюда и «ожидается строка вида scrypt$N$r$p$соль$ключ» на `/admin`: сервер получал непустой, но искалеченный хэш. Падали ровно шесть сквозных сценариев — те шесть, что отправляют пароль. `SESSION_SECRET` знака `$` не содержит и потому уцелевал, оттого остальные сценарии были зелёными.

*Главное, что нашлось по ходу.* Это не дефект тестов. Тот же замер во втором случае — «хэш записан в `.env`, как велит инструкция проекта» — даёт ровно то же превращение. То есть документированный локальный порядок работы (посчитать хэш скриптом, положить в `.env`, поднять `npm run dev`) **не работал никогда**: вход отказывал бы и разработчику. Сквозные сценарии просто первыми на это наступили.

*Как починено и почему так.* Разделитель в формате хэша — точка вместо `$` из PHC. Рассмотренные и отвергнутые направления: отдельный файл окружения для прогона (`.env.test`, `.env.production.local`) — подстановка калечит значения из любого файла, а не только из `.env`; поднятие тестового сервера мимо `.env` — чинит прогон и оставляет сломанной локальную разработку; экранирование `$` как `\$` в примере — работает, но требует помнить об этом при каждой перегенерации хэша, а забывший получает молчаливую порчу. Точка снимает целый класс отказов сразу: в base64url её нет, разбор однозначен, подстановке зацепиться не за что. Регрессия закрыта проверкой на **настоящем** загрузчике Next (`env-file.test.ts`, `@next/env` заведён в devDependencies) плюс отдельной — что в формате хэша нет `$`.

### T104 — мигающая проверка «постоянного времени»

**Делал сам:** это код аутентификации и разбор того, что именно гарантирует проверка, — прямое исключение из условия делегирования, как и вся остальная работа блока.

_Что мигало — фактом, а не по названию._ Нестабилен был один тест: `password.test.ts` → «сравнение постоянного времени › неверный пароль отвечает не быстрее верного». Он падал двумя разными способами, и оба — не про регрессию:

- под покрытием `expected 56.49 to be greater than 69.30`, то есть не сработал порог `wrong > right * 0.7`;
- без покрытия `Test timed out in 5000ms` — тело теста делает 30 вычислений `scrypt` при `N=2^14` и в бюджет одного теста на загруженной машине не укладывается.

Отдельно я прогнал файл в своей копии: сам по себе он зелёный всегда (3 прогона с покрытием, 13 тестов), под искусственной нагрузкой на все 10 ядер — тоже (3 прогона). Поймать падение «по требованию» нельзя, что для замера настенных часов и ожидаемо.

_Почему он мигал — замер меряет не то, что называет._ Ветки «верный пароль» и «неверный пароль» выполняют **одну и ту же работу**: один полный `scrypt` и один `timingSafeEqual`. Значит разницы во времени между ними нет по построению, и тест меряет чистый шум. Хуже того, в замере зашит систематический перекос: `right` — минимум из 7 замеров, а `wrong` — минимум из трёх таких минимумов, то есть из 21. Минимум по большей выборке всегда ниже, поэтому отношение смещено вниз независимо от кода. Замерено зондом, где **по обе стороны стоял один и тот же верный пароль**, а различалась только форма выборки:

```
round=0 right=23.84 тот-же-верный-как-неверный=22.19 ratio=0.931
round=1 right=22.31 тот-же-верный-как-неверный=20.75 ratio=0.930
round=2 right=21.04 тот-же-верный-как-неверный=20.13 ratio=0.957
round=3 right=19.81 тот-же-верный-как-неверный=19.77 ratio=0.998
round=4 right=19.29 тот-же-верный-как-неверный=19.18 ratio=0.994
round=5 right=21.56 тот-же-верный-как-неверный=19.83 ratio=0.920
```

Отношение никогда не выходит выше 1 даже там, где сравнивать нечего. Порог `0.7` — это «сколько шума мы терпим, пока перекос его не перекроет», а не свойство кода.

_Главная находка: проверка не ловила того, ради чего написана._ Прогнал **прежний** замер против трёх порч `verifyPassword` и сравнил с новой проверкой:

| Порча `verifyPassword`                              | Прежняя (замер часов)                                | Новая (сверка работы)                                   |
| --------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| A — `derived.equals(key)` вместо `timingSafeEqual`    | **пропускала** (1 passed)                            | ловит: `expected [ Array(1) ] to strictly equal [ …(2) ]` |
| B — `if (password.length < 8) return false;` до scrypt | ловит: `expected 0.00087 to be greater than 12.59`   | ловит: `expected [] to strictly equal [ …(2) ]`           |
| C — сравнение половины ключа (`subarray(0, 16)`)      | **пропускала** (1 passed)                            | ловит: `expected [ …(2) ] to strictly equal [ …(2) ]`     |

Замер ловил только грубый ранний возврат (B) — ровно ту порчу, на которой он и был когда-то проверен (см. запись T013: «ранний выход по длине пароля валит замер времени, 0,0008 мс против 13,1 мс»). Обе порчи, которые ломают **именно постоянство времени сравнения**, он пропускал молча. Мигающий тест здесь был не просто шумным — он создавал ложное ощущение, что свойство проверено.

_Что стало вместо замера._ Проверяется сама работа, а не часы. `node:crypto` подменён обёрткой, которая выполняет настоящие `scrypt` и `timingSafeEqual`, но записывает в журнал каждый вызов: соль, длину ключа, `N/r/p`, длины сравниваемых буферов и порядок. Сам пароль в журнал не пишется — он единственное, чему позволено различаться. Две проверки:

1. «неверный пароль проходит ровно ту же работу, что и верный» — журнал для четырёх видов неверного (короче, той же длины, отличается одним знаком, пустой) совпадает с журналом верного. Ловит любой ранний возврат.
2. «путь неверного пароля доходит до `scrypt` и до `timingSafeEqual`, а не отваливается раньше» — журнал равен ровно `["scrypt соль=… ключ=32 N=1024 r=8 p=1", "timingSafeEqual 32=32"]`. Нужна отдельно: если бы сравнение шло через `Buffer.equals`, первая проверка осталась бы зелёной (обе ветки сломаны одинаково), а эта падает.

Проверка перестала зависеть от скорости машины и подешевела: время тестов файла 658 мс → 42 мс, вычислений `scrypt` при `N=2^14` не осталось вовсе.

_Дефекта в коде не нашлось._ `verifyPassword` действительно постоянного времени: `parseStored` зависит только от хранимого хэша, но не от пароля; `derive` считается всегда целиком; длина производного ключа берётся из хранимого, поэтому раннего выхода по длине нет; сравнение — `timingSafeEqual`. Путь вызова тоже чист: в `signIn` до `scrypt` стоит только предел попыток (T066), и он смотрит на клиента, а не на пароль, — то есть срабатывает одинаково и на верном, и на неверном. `rate-limit.ts` не трогал.

_Что нашёл по дороге и не чинил._ `scripts/check` зовёт Playwright без порта, и тот берёт общий 3101 мимо диапазонов блоков: два блока разом получают ложное падение или чужой сервер. Обошёл прогоном `E2E_PORT=3261 ./scripts/check`; сам файл общий и правится диспетчером при слиянии.

**Проверено запуском.** Задача про нестабильность, поэтому `./scripts/check` прогнан дважды подряд — один зелёный прогон здесь ничего не доказывает. Оба прогона совпали до числа:

| Прогон | Модульные | Сквозные | Итог |
| --- | --- | --- | --- |
| 1 | 856 в 78 файлах, 0 провалов | 117 passed (30,6 с) | ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ |
| 2 | 856 в 78 файлах, 0 провалов | 117 passed (27,4 с) | ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ |
