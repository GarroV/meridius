# Block: demo

## Назначение

Демонстрационный контур и запуск продукта на локальной площадке: чтобы показать коллегам, ничего не заводя руками.

## API-контракт

```
npm run seed:demo     # идемпотентный сид, повторный запуск не плодит дубликаты
```
Данные демо — английские (правило проекта), отдельная демонстрационная страна, не смешивается с рабочими данными.

## Зависимости

`catalog`, `editor`, `fill`, `feed`

## Definition of Done блока

1. Сид создаёт демонстрационную страну, две пиццерии, станции с кодами, три чек-листа с секциями и переиспользуемым блоком и десяток заполнений, включая одно с проваленным критичным пунктом.
   С 09.09.2026 контур показывает и режимы смены: у центральной пиццерии на сегодня стоит смена с ограничениями (2 из 4), одно вечернее заполнение сделано в критичную смену, а пункты разведены по трём уровням.
   Время заполнений задаётся местными сутками и местным временем пиццерии (`daysAgo` + `at`), а не сдвигом «столько часов назад»: заполнение обязано попадать ВНУТРЬ окна своего чек-листа при любом времени показа. Со сдвигом вечернее закрытие оказывалось «заполненным» в полдень, лента показывала его выполненным, а полоса тревог — пропущенным; оба утверждения были верны и вместе читались как дефект продукта ровно на показе. Инвариант держат проверки в `dataset.test.ts`.
   Вечернее закрытие за прошедшую ночь оставлено незаполненным НАМЕРЕННО: это вторая тревога, которую демо показывает.
   С 10.09.2026 контур показывает и третью — критичный пункт, оставленный БЕЗ ОТВЕТА: сегодняшнее утреннее заполнение полное, кроме замера температуры поставки. Это единственное неполное заполнение контура, и проверка покрытия делает исключение только ему. Тревога считается лишь по заполнениям за текущие местные сутки, поэтому `daysAgo` у него обязан оставаться нулём.
2. Повторный запуск сида возвращает контур в исходное состояние и не плодит дубликаты — проверено двойным прогоном.
3. Продукт поднимается на локальной площадке одной командой, адрес открывается в браузере.
4. Сквозной сценарий MVP проходит на поднятом продукте целиком: от создания чек-листа до появления заполнения в ленте.
5. Демонстрационные данные не попадают в рабочую страну.

## Решения, принятые внутри блока

| Решение | Почему |
|---|---|
| Идемпотентность устроена как «снять своё и завести заново», а не «досоздать недостающее» | Досоздание требует сравнивать каждую строку с описанием и разбирать частичные расхождения — ровно тот код, который тихо расходится с данными. Опознаватели контура постоянны, поэтому снятие точечное и чужой строки не касается |
| Заполнения снимаются по СТАНЦИИ контура, а не только по своему опознавателю | На показе по демо-коду заполняют по-настоящему; такая запись держала бы версию внешним ключом, и второй прогон сида падал бы вместо обновления контура |
| Времени в описании контура нет — только смещения назад от опорного момента | Иначе демо через месяц показывает ленту месячной давности, а два прогона нельзя сравнить строка в строку |
| Два чек-листа одной станции закрывают сутки целиком | Демо обязано открываться по QR в любой час: чек-лист с утренним окном вечером не открылся бы, и продукт выглядел бы сломанным |
| Данные демо — только английские, ключ `en` единственный | Правило проекта (конституция, «Демонстрационный режим»). Русское устройство увидит английский текст: `pickText` откатывается к первому имеющемуся языку |
| Запуск сида идёт через хук разрешения импортов, а не отдельной копией запросов в `.mjs` | Node умеет исполнять TypeScript, но не знает псевдонима `@/` из tsconfig. Без хука сид пришлось бы писать мимо слоя доступа — второй набор запросов к базе, который разъедется со схемой |
| Смоук MVP — отдельный сценарий с параметром адреса, а не ещё один файл в `e2e/` | Он обязан гоняться по ПОДНЯТОМУ продукту, в том числе после раскатки на площадку (T079), а `e2e/` поднимает свой сервер и свою базу |

Исключение проверил: оно не ослабляет проверку до пропуска, а сравнивает с тем же списком минус один пункт. Дописал связку между двумя требованиями — что тревогу поднимает ИМЕННО то заполнение, которому сделано исключение, и что без ответа остался именно тот пункт: иначе они могли разъехаться молча. **Проверка в продукте, а не в счётной функции:** `listAlarms` на живой базе стенда даёт `criticalFailed 1, criticalUnanswered 1`, а после закрытия вечернего окна — все три вида: `criticalFailed 1, criticalUnanswered 1, missed 1` |

Нарушение не спрятано: axe остался без `disableRules` и `exclude`, а страница без заголовка уронит шаг по таймауту с текстом. **Проверка:** до починки полный прогон упал на первом же заходе, после — 6 полных прогонов подряд по 102 сценария зелёные |

Продукт таких ответов не создаёт вовсе — `isAnswered` в блоке fill считает текст из одних пробелов НЕотвеченным пунктом, — то есть на карточке заполнения строка «Notes for the day shift» показывалась бы пустой и читалась как «поле не сохранилось». ## Как продукт живёт на площадке MUSPELHEIM

> Заведено 07.09.2026 (D038, D043, D046). Раскатка выполняется только по явному «да» владельца.

Папка на площадке — `C:\projects\meridius`, клон этого репозитория. Своё имя стенда
в Docker (`COMPOSE_PROJECT_NAME=meridius`), приложение на порту 3100, база на `127.0.0.1:5455`
и наружу НЕ публикуется: порт 5433 там занят чужим проектом, а публичной точке записи внешняя
база не нужна. На контейнере базы стоит метка `backup.pgdump=true` — по ней её забирает ночной
бэкап площадки (03:30, ретеншн 14 дней).

Секреты площадки свои, не демонстрационные из `.env.example`: пароль кабинета, секрет подписи
сессии и пароль базы. Файл `.env` лежит только на площадке и в git не попадает.

На время показа в кабинете стоит короткая единая учётка по требованию владельца (D047): порог
длины у `scripts/hash-admin-password.mjs` не снят, а пройден явным флагом `--allow-short`.
Значение пароля не пишется ни в один файл репозитория — он публичный; пароль знают владелец и
`.env` площадки. После показа его меняют на длинный.

Наружу продукт отдаёт отдельный туннель Cloudflare (`C:\bootstrap\cloudflared.exe`), продукт
живёт на корне своего адреса. Публиковать его на пути порта Tailscale нельзя, пока не закрыта
T088: обычные ссылки между экранами базового пути не знают.

Два процесса держатся задачами планировщика, а не SSH-сессией (иначе `sshd` убивает дерево
процессов при выходе):

| Задача | Что делает |
|---|---|
| `meridius-start` | `npm run start` — продукт на порту 3100, журнал в `run.log` |
| `meridius-tunnel` | `cloudflared tunnel --url http://localhost:3100`, журнал в `tunnel.log` |

Порядок обновления продукта на площадке: `git pull` → `npm ci` (если менялись зависимости) →
`npm run build` → остановить процесс продукта → `schtasks /Run /TN meridius-start`. Пересборка
обязательна при смене любого значения окружения: значения запекаются в сборку (D033).

Проверка после обновления — одной командой с машины разработчика:

```bash
node scripts/mvp-smoke.mjs --url <публичный адрес> --password <пароль кабинета> --timeout 90000
```

Шаг ожидания задаётся флагом `--timeout`: через туннель ответы идут медленнее, и значения по
умолчанию не хватает.

**Смоуку нужна база, и без неё он не стартует** (T089). Он проходит продукт настоящими
действиями, значит оставляет настоящие строки, а убрать их средствами самого продукта нельзя,
и это не недоделка: заполнения не удаляются вовсе (`submissions` — `ON DELETE RESTRICT`,
история неприкосновенна), а чек-лист с заполнениями продукт снимает с работы, а не стирает
(`removeChecklist` блока editor). Поэтому уборка идёт через слой доступа, и `DATABASE_URL`
обязателен: без него смоук отказывается начинать, а не заводит данные, которые потом некому
убрать. С машины разработчика к закрытой базе площадки — через проброс `ssh -L`.

Уборка вызывается трижды: на входе (снять брошенное прошлыми прогонами — прогон, убитый
Ctrl-C, до `finally` не доходит), в `finally` (снять своё, в том числе после падения
посередине) и по сигналу обрыва. До и после прогона смоук сверяет перепись базы с описанием
демо-контура и печатает расхождение по таблицам; расхождение до прогона — отказ стартовать
(на неизвестном стенде проверка «после прогона ровно демо-контур» ничего не значила бы).

**Почему уборки по имени страны не хватало.** `checklists.station_id` объявлен
`ON DELETE SET NULL` осознанно — удаление станции отвязывает чек-лист, но не уничтожает его
историю (см. `src/blocks/data/schema.ts`). Уборка по стране сносила станцию, а чек-лист
оставляла — уже без станции, то есть не находимым ни по стране, ни в справочнике: 07.09.2026
таких набралось восемь при трёх настоящих. Отсюда два правила в `src/blocks/demo/smoke.ts`:
метку `Smokeland` несут ВСЕ имена прогона, включая название чек-листа (по ней отвязанный
чек-лист и находится, и его нельзя спутать с тем, который методист отвязал сам через
`detachChecklist`), а чек-листы снимаются РАНЬШЕ станций — тогда отвязанных не появляется
вовсе. Проверка `забирает и чек-лист, отвязанный от станции` в `smoke.test.ts` написана
ровно на этот случай и падает, если уборка снова возьмёт только один слой.

Ожидаемое содержимое демо-контура смоук считает из самого описания (`contourCensus`), а не
