# Block: data

## Назначение

Схема данных, миграции и единственный слой доступа к базе. Все остальные блоки ходят в данные только через него — это и архитектурное решение, и правило, проверяемое границами модулей.

## API-контракт

```ts
// схема
countries, stores, stations, checklists, checklist_versions, blocks, submissions

// типы
type Item = { id: string; title: Record<string,string>; type: 'bool'|'number'|'text'|'table';
              severity?: 'critical'|'major'|'normal'; critical?: boolean;   // critical — только чтение старого
              min?: number; max?: number; unit?: Record<string,string>; hint?: Record<string,string>;
              schedule?: ScheduleSegment[]; remindEveryMinutes?: number; columns?: ItemColumn[] }
type Section = { id: string; title: Record<string,string>;
                 source: 'own' | { blockId: string }; items: Item[] }
type Answer = { itemId: string; value: boolean|number|string; comment?: string; at: number }

// функции
getPublishedVersionForStation(stationCode: string, at: Date): Promise<VersionWithChecklist | null>
getDraft(checklistId: string): Promise<ChecklistVersion | null>
publishVersion(checklistId: string): Promise<ChecklistVersion>   // вставка строки, не update
saveSubmission(input: { versionId: string; answers: Answer[]; startedAt: number }): Promise<string>
listSubmissions(filter: { countryId?; storeId?; stationId?; from?; to? }): Promise<SubmissionRow[]>
getSubmission(id: string): Promise<SubmissionDetail | null>
```
Частичный уникальный индекс: одна опубликованная версия на чек-лист. Все отметки времени сервера — `now()` базы, не клиентские.
Одно заполнение — одна запись (миграция 0012, T219): вторую запись с той же парой «версия + начало» `saveSubmission` не сохранит — база отказывает нарушением уникальности `submissions_one_per_filling_idx`. Повторы, легшие до правила, остаются в истории с пометкой `submissions.duplicate` и из-под правила выведены.

## Зависимости

`core`

## Definition of Done блока

1. Миграции применяются с нуля и откатываются.
2. `publishVersion` создаёт новую строку, прежняя версия побайтово не меняется — тест сравнивает содержимое до и после.
3. `getPublishedVersionForStation` возвращает версию по окну времени: утренний чек-лист в 09:00, вечерний в 21:00, `null` в 15:00, если ни одно окно не подходит.
4. Заполнение ссылается на конкретную версию; после публикации следующей версии старое заполнение читается без изменений.
5. Неизвестный код станции даёт `null`, а не исключение и не чужие данные.
6. Покрытие слоя доступа тестами с реальной базой в контейнере.

## Решения, принятые внутри блока

| Решение | Почему |
|---|---|
| У версии три состояния: `draft`, `published`, `archived` | Частичный уникальный индекс держит одну опубликованную версию на чек-лист. Публикация следующей версии переводит прежнюю в `archived` — меняется только признак, содержимое (секции, номер, время публикации) остаётся тем же байт в байт |
| У черновика нет номера версии и времени публикации, у опубликованной и архивной — есть | Ограничение `check` в базе: состояние и номер не разъезжаются даже при вставке мимо слоя доступа |
| Один черновик на чек-лист — тоже частичным уникальным индексом | `getDraft` по контракту возвращает одну строку; два черновика сделали бы ответ недетерминированным |
| Удаление страны, пиццерии, станции и версии запрещено, пока на них ссылается история (`on delete restrict`) | Принцип 3: история заполнений неприкосновенна. Исключение — `checklists.station_id`: удаление станции отвязывает чек-лист (`set null`), но не трогает ни его, ни заполнения |
| Чек-лист с заполнениями не удаляется, а помечается снятым: `checklists.archived_at` (миграция 0005) | Тот же принцип 3 с другой стороны. Стереть такой чек-лист нельзя — на его версии ссылаются заполнения, и в них хранится снимок пунктов, которые видел сотрудник. Но методисту нужно убрать чек-лист из работы, и «удалить нельзя» было бы тупиком. Поэтому снятый чек-лист уходит из списка (`listChecklists`) и перестаёт открываться на станции (`getPublishedVersionForStation`), а история остаётся целой. Чек-лист без заполнений удаляется по-настоящему, вместе с версиями |
| Заполнение хранит `station_id` рядом с `version_id` | Перенос чек-листа на другую станцию (T024) не должен задним числом переписывать, где заполняли |
| Станция замораживается в `checklist_versions` при публикации, и заполнение берёт её оттуда | `checklists.station_id` — обычная мутируемая колонка: читать её в момент сохранения значит записывать заполнение туда, куда чек-лист перевязали, пока сотрудник заполнял (T056). Клиент станцию по-прежнему не передаёт: она выводится сервером из версии |
| `getPublishedVersionForStation` отдаёт версию, только если её замороженная станция совпадает со сканируемой | Иначе заморозка ломает вторую половину сценария: после переноса чек-листа станция B получала бы версию, замороженную на A, и заполнение с B уходило бы в историю A. Следствие: после переноса чек-листа его надо опубликовать заново — на новой станции до этого ничего не отдаётся |
| Пустое окно (`window_start = window_end`) запрещено базой, а окно через полночь разрешено | Равные границы делают условие выбора версии всегда ложным: чек-лист не открывается никогда и молча. Конец раньше начала — наоборот, штатный вечерний чек-лист |
| У пиццерии есть часовой пояс, и окно чек-листа сравнивается с её местным временем | Этого требует контракт блока `catalog` (`createStore({ countryId, name, timezone })`), и без пояса утренний чек-лист в стране с большим сдвигом открывался бы среди дня. Момент времени переводится в пояс пиццерии прямо в запросе |
| Снимок для ленты и карточки читается из строки заполнения, а не из версии | Иначе вторая опора истории (D002) мнимая: снимок хранится, но не используется, и одной правки версии мимо слоя доступа хватает, чтобы переписать показанное сотруднику |
| Верхняя граница размера JSONB стоит в базе, а не только в блоке `fill` | `submissions` — единственная таблица, куда пишет неопознанный человек из интернета. Если единственная защита живёт в коде вызывающего, забытая проверка означает, что база примет что угодно |
| Строка ленты отдаёт оба счёта провалов: `failedCount` (всего) и `failedCriticalCount` (критичные) | Одного критичного счёта экрану не хватает: столбец «Результат» обязан отличать «всё выполнено» от «два пункта не выполнены». Пока строка отдавала только критичные, лента дочитывала остальное вторым запросом по уже отобранным id (`feed/failures.ts`) — второй запрос на каждую отрисовку и второе место, где живёт правило провала. Оба числа считаются по снимку и ответам, которые `listSubmissions` и так читает, то есть новое поле не стоит ни запроса, ни колонки в базе (T100) |
| `listSubmissions` ограничивает выдачу (по умолчанию 200 строк, параметр `limit`) | Лента без предела — запрос, который растёт вместе с историей |
| Тексты CHECK-ограничений канонизирует сам PostgreSQL, а не регулярные выражения в тесте | Схема и база пишут одно условие по-разному: `locale in ('ru','en')` база печатает как `locale = ANY (ARRAY['ru'::text, 'en'::text])`, `between 1 and 240` — как `>= 1 AND <= 240`. Приводить одно к другому руками значит писать в тесте свой разбор SQL: он краснеет на шуме, а чинят такое ослаблением сравнения, пока оно не перестанет ловить подмену. Поэтому объявленное в схеме вешается на временную копию таблицы (`create temp table (like …) on commit drop`), и обе стороны читаются одним `pg_get_constraintdef`. Настоящие таблицы не трогаются |
| Единица измерения пункта — `LocalizedText`, как `title`, `hint` и норма колонки, а не одна строка | «кг» и «kg» — одна единица на двух языках, и одной строкой русская подпись уехала бы на английский экран. У «°C» и «%» обе подписи совпадут, но ломать общее правило разметки ради одного поля нельзя. Редактору это ничего не усложняет: норма колонки уже правится одним полем на текущем языке (`editing.ts`), единица правится так же |
| Тестовая база отдельная (`TEST_DATABASE_URL` или рабочая с суффиксом `_test_<метка копии>`) | Прогон тестов пересоздаёт схему с нуля; на рабочей базе это стёрло бы данные разработчика |
| У пула есть пределы: запрос — 10 с, ожидание свободного соединения — 3 с, соединений — 10 | Маршрут заполнения открыт в интернет, и под всплеском отказ обязан приходить быстро, а не копиться очередью. Десять секунд — это уже не «медленный запрос», а зависший: самая тяжёлая выборка продукта (лента одной станции) ограничена 200 строками и идёт по составному индексу, то есть измеряется миллисекундами; такой запрос база снимает сама и возвращает соединение в пул. Три секунды ожидания — стократный запас к штатным десяткам миллисекунд и при этом быстрый отказ вместо спиннера: сотрудник пересканирует код. Десять соединений заданы явно, а не унаследованы у драйвера: совпадение с его нынешним умолчанием — не решение, и обновление драйвера не должно менять нагрузку на базу молча. Десятки сканирований в минуту на пересменке эти десять соединений перекрывают многократно, а бюджет PostgreSQL (`max_connections` = 100, проверено на стенде) остаётся свободен для миграций, `psql` и второго экземпляра приложения во время выкладки. Миграции идут мимо этого пула (свой `Pool` в `migrator` и в подготовке тестовой базы), поэтому предел времени запроса не режет длинный DDL |
| Город и код точки — колонки `stores.city` и `stores.code`, обе необязательны; код уникален в стране индексом `stores_country_code_uq` (миграция 0017, #141) | Импорт справочника опознавал пиццерию по имени, и переименование на экране давало дубль. Уникальный индекс, а не ограничение таблицы: пустые значения в нём различны, и 145 пиццерий без кода остаются валидными. Заполнять код догадкой миграция не вправе — его нет в источнике. Пустая строка и пробел по краю запрещены CHECK: «P-1» и «P-1 » были бы одной точкой для человека и двумя для индекса |
